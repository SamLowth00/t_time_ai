0 · The cheat sheet

If you only re-read one thing — this. Everything else is the "why".

The one question that decides your concurrency tool

Is the CPU working hard, or is it waiting? Working hard (computing) → processes/Workers. Waiting (network, disk, DB) → asyncio or threads.

Your work is…Library situationUseWhy
I/O-bound (waiting)async-native libs (aiohttp, async Playwright)asyncioone thread fills idle wait time; cheap; scales to thousands of tasks
I/O-bound (waiting)only blocking/synchronous libs (requests, legacy SDK)threadingworks with any library; OS preempts threads; GIL released during I/O
CPU-bound (computing)anymultiprocessing / Workersreal parallelism across cores; only way past the GIL

Two things that are NOT the deciding factor

Code complexity — a 1,000-line system can be I/O-bound; a one-liner can be CPU-bound. And "is it a background job?" — that's a separate, orthogonal question (just whether you await it or detach it). Neither tells you which tool to use. Only the bottleneck does.

1 · CPU-bound vs I/O-bound

The foundational concept — everything else hangs off it. "Bound" means "bottlenecked by". When a task runs, it's in one of two states:

  • Actively using the CPU — calculating, transforming data. → CPU-bound
  • Waiting for something external — network, disk, database. CPU sits idle. → I/O-bound

The litmus test

Would a faster CPU make this finish sooner? Yes → CPU-bound. No (you're waiting on a network/disk that's just as slow) → I/O-bound.

CPU-bound — a core pinned at 100%

Heavy math, image resizing, video transcoding, compression, sorting huge lists, ML inference, rendering a web page.

I/O-bound — CPU mostly idle, waiting

Downloading a file, querying a database, reading from disk, calling an API.

Analogy — the chef

CPU-bound = the chef chopping vegetables. The hands (CPU) are the bottleneck — only faster hands or more chefs help. I/O-bound = the chef put a dish in the oven and waits 20 minutes. The hands aren't the bottleneck; the oven time is. A faster chef changes nothing — but the chef can start another dish while waiting. That's concurrency.

In this project

The Python backend is I/O-bound — it sends a request to Google Places and waits, tells Playwright to load a page and waits. → asyncio. Rendering the pages is CPU-bound — that's Chromium parsing HTML, running JS, painting. → it runs in separate Chromium processes. The architecture split itself correctly along the bottleneck line.

2 · Concurrency vs parallelism

They sound like synonyms. They're not.

Concurrentmultiple tasks in progress over the same period, interleaved on one thread — taking turns. At any single instant, only one is actually running.
Parallelmultiple tasks executing at the same instant, on different CPU cores. Genuinely simultaneous.

asyncio.gather(...) is concurrent, not parallel. It schedules many coroutines on one event loop, on one thread — they take turns at await points. The discovery code's gather of 8 workers is 8 coroutines on one thread, not 8 cores.

Analogy — one chef, 8 dishes

The chef does one action at a time, but while dish 1 is in the oven (the await — the waiting), the chef chops for dish 2, stirs dish 3. The waiting overlaps; the chef's active work never does. 8 oven-heavy dishes finish nearly as fast as 1. 8 all-chopping dishes take 8× as long — there's no waiting to overlap.

Which is exactly why gather is brilliant for I/O-bound work (the waits overlap) and useless for CPU-bound work (no waiting to fill — for that you need real parallelism).

3 · Preemptive vs cooperative multitasking

Both share limited CPUs among many tasks. They differ on one question: when it's time to switch tasks — who decides?

PreemptiveCooperative
Who switchesan external scheduler (the OS), anytimethe task itself, at points it chooses
Triggerhardware timer interrupt (~every few ms)an explicit await / yield
Shared statecan be caught half-updated → needs locksatomic between yields → rarely needs locks
Switch costhigher (kernel round-trip)lower (in-process)
One bad taskcontained — scheduler yanks itfreezes everything — nothing can preempt it
ExamplesOS threads & processesasyncio, JS event loop, generators

Analogy

Preemptive = a classroom with a strict teacher and a stopwatch — the teacher cuts off any student mid-sentence. Cooperative = a conversation among polite adults passing a talking stick — you speak until a natural pause, then hand it over yourself. Efficient and civil, until one person monologues forever and everyone's stuck.

The history is the interesting part

At the OS level, the world moved away from cooperative — Windows 3.x and classic Mac OS were cooperative, and one frozen app hung the whole machine. The shift to preemptive was a stability win. But inside a single program, cooperative came back (asyncio, Node, Go) — because there you control all the code and can trust it to yield, buying cheap switches and lock-free atomic-between-yields. Preemptive is about distrust; cooperative is about trust + efficiency.

4 · asyncio & coroutines

Calling an async def runs zero lines of it

This is the thing to internalise. A regular function call runs the body. An async def call does not — it builds an inert coroutine object (a "frozen plan") and hands it back. Not even the first line runs.

async def say_hello():
    print("hello!")

say_hello()    # prints NOTHING. Returns <coroutine object>.
               # (and warns: "coroutine was never awaited")

To actually run it, something must drive it:

What you writeBody runs?Driven by
_run_job(...)nonobody — coroutine created, then discarded
await _run_job(...)yesthe current coroutine — which blocks until it finishes
asyncio.create_task(_run_job(...))yesthe event loop, concurrently — caller does not wait

"There is no background"

A bare call doesn't "run in the background later" — there is no ambient background. "The background" is the event loop's task list. Code only runs concurrently if it's been registered with the loop as a Task. create_task does that registration; a bare call doesn't, so the coroutine is just garbage-collected, unrun.

The event loop only switches at await

The single rule that fixes the whole mental model:

No await, no switch. A synchronous function runs atomically — it cannot be preempted. So start_job (a plain def with no await) runs start-to-finish uninterrupted; _run_job doesn't interleave with it — it waits in the ready queue until start_job is done and the call chain hits an await.

The loop's actual tick: take a ready task → run it until it suspends or finishes → move any newly-unblocked tasks into "ready" → repeat. (A suspended task isn't polled — it's moved back into the ready queue when the thing it waited on completes.) And await only hands control back if the awaited thing isn't ready yet; awaiting something already complete just continues straight through.

Payoff & danger

Payoff: code between awaits is atomic, so you rarely need locks — the await-free spans are your critical sections, for free. Danger: a blocking call (time.sleep, a sync DB driver, a heavy CPU loop) has no await — it freezes the entire loop, every task, because nothing can preempt it. This is why the scrapers use Playwright's async API.

JavaScript trap (for JS people)

In JS, calling an async function runs its body synchronously up to the first await, then returns a promise. Python is stricter: calling runs nothing, and create_task is fully lazy — even the synchronous head of the function doesn't run until the loop next gets control. Same keyword, different "when does it start" rule.

5 · Semaphores

The simplest concurrency primitive: a counter with two operations.

  • acquire — counter above zero? decrement and proceed. Counter at zero? suspend until a slot frees.
  • release — increment the counter; wake the next waiter if there is one.
async with SEMAPHORE:     # acquire (waits here if counter is 0)
    do_the_work()         # at most N coroutines are ever inside this block
# release on the way out — automatically, even on exception or cancellation

The async with matters: it guarantees the release happens on every exit path. Hand-rolled acquire/release that skips a release on an exception permanently leaks a slot.

asyncio.Semaphore(1) is just a lock. A semaphore is the generalisation: "a lock, but N holders allowed."

Where does a waiting job actually live?

When job #6 hits a full semaphore, acquire() creates a Future, parks it in the semaphore's internal _waiters deque, and awaits it. So:

The Future ("your ticket")the semaphore's _waiters deque
The Task + coroutine + all its frozen local variablesthe event loop's task registry, suspended

The semaphore doesn't store "the job" — it stores a Future. release() completes that Future, the loop reschedules the Task, and _run_job continues under its own power. (And note: job #6 has already started — it ran its first couple of lines, then froze on the async with line. It's a started function parked mid-body, not a queued one waiting to begin.)

Analogy — the restaurant host

The semaphore is a host with a clipboard. When the place is full, the host writes a ticket on the waitlist (the Future in _waiters). But you aren't on the clipboard — you're standing by the door (the event loop). When a table frees, the host calls the next ticket (fut.set_result()), and that call is what tells you to walk in.

Gotcha — Python 3.9 loop binding

On Python 3.9, asyncio.Semaphore() binds to whatever event loop exists when it's constructed. Built at import time, that's not uvicorn's serving loop — and the first job that actually has to wait raises got Future attached to a different loop. (Acquiring a free slot is fine — it just decrements an int, no loop involved. Only waiting touches the loop. That asymmetry is the tell.) Fix: build it lazily, on first use, inside a function that runs on the serving loop. Python 3.10+ binds lazily on its own.

In this project

MAX_CONCURRENT_JOBS = 5 caps concurrent discovery jobs. Each job runs 8 worker coroutines that can each drive a Playwright context → peak 5 × 8 = 40 Chromium contexts (~2–4 GB RAM). It's the backstop for when per-IP rate limits get bypassed by many distinct IPs. It wraps _run_job (the background task), not the route handler — so the POST stays fast and the wait happens silently in the background.

6 · Threading & the GIL

threading.Thread() creates real OS threads — multiple threads, but all inside one process, sharing memory. That shared memory is the source of both threading's convenience and its hazard.

The race condition

counter = 0
def increment():
    global counter
    for _ in range(1_000_000):
        counter += 1            # NOT atomic — it's load, add, store

# two threads running this → final counter is reliably LESS than 2,000,000

counter += 1 is three steps (read → add → write). Threading is preemptive — the scheduler can switch between those steps. Two threads both read 5, both write 6; one increment is lost.

A Lock fixes it

lock = threading.Lock()
def increment():
    global counter
    for _ in range(1_000_000):
        with lock:              # acquire — block if another thread holds it
            counter += 1        # only one thread can be in here at a time

A Lock (mutex) has two states, locked/unlocked. acquire() blocks the thread until the holder releases. It makes the block effectively atomic. (And — a Lock is conceptually Semaphore(1). It's also exactly the lock you don't need in asyncio, because non-await code is already atomic.)

The GIL — Global Interpreter Lock

CPython has one lock that a thread must hold to execute Python bytecode. So even with many threads on a multi-core machine, only one runs Python bytecode at any instant — the rest wait for the GIL. It's handed off two ways at once: preemptively (taken away ~every 5 ms) and cooperatively (voluntarily released during blocking I/O). The GIL is essentially a Semaphore(1) around "running Python code".

That second handoff — released during I/O — is why threading still helps I/O-bound work: while thread A waits on a network reply, it isn't holding the GIL, so thread B runs. But for CPU-bound pure-Python work, threading gives almost nothing — the GIL serialises it. 4 threads crunching numbers on 4 cores run about as fast as 1.

The limit is only on Python bytecode. Two threads both waiting on network I/O genuinely overlap. "Python can't use two cores" is wrong — "Python bytecode can't run on two cores at once" is right.

7 · Processes & Workers

Python multiprocessing and JavaScript Workers are the same idea: a separate "computer" you talk to by sending letters. Its own memory, its own everything — you can't touch its variables, it can't touch yours.

# Python — a whole new interpreter per process, each with its OWN GIL
from multiprocessing import Pool
with Pool(4) as pool:
    results = pool.map(heavy, [10_000_000] * 4)   # 4 cores, genuinely parallel
// JavaScript — a separate JS context, own heap
const worker = new Worker('worker.js');
worker.postMessage({ n: 10_000_000 });
worker.onmessage = (e) => console.log('result:', e.data);

Isolation by design

No shared memory → no race conditions, no locks → safe, genuine parallelism. The cost: communication is message passing — data is serialized and copied across the boundary (pickling in Python, structured clone in JS), and startup is heavyweight (a whole interpreter / JS context — so you pool and reuse them).

ThreadProcess / Worker
Memorysharedisolated (own copy)

One crashescan take down the processisolated — others survive

Reach for them when the work is CPU-bound — heavy math, media processing, ML, compression. In a browser, even a single Worker is worth it just to get a heavy loop off the main thread so the UI doesn't freeze.

In this project

You're already using process isolation — every Chromium that Playwright launches is a separate OS process with its own memory. The "40 browsers" under the semaphore are 40 isolated processes — which is exactly why they cost 2–4 GB RAM. The Python backend stays async (I/O-bound coordination); the CPU-heavy rendering is handed off to those separate processes. Textbook division of labour.

8 · JavaScript's model (and how it maps)

Your JavaScript code: genuinely one thread, one call stack. Two pieces of your JS never run at once. While the call stack is non-empty, nothing else runs — the event loop pulls the next callback only when the stack is empty. Same cooperative model as Python's asyncio, same failure mode (a long sync loop freezes everything).

The runtime around it: absolutely multi-threaded. When you fetch() or set a timer, the actual I/O happens on the browser's / Node's other threads (Node's libuv keeps a thread pool). They just hand results back to your one thread's event loop. "Single-threaded" describes the programming model, not the process.

Workers are real extra threads — but isolated, message-passing, no shared memory. More like Python multiprocessing than threading.

The key mapping

JS is "one thread, many tasks" — that's Python asyncio, not Python threading ("many threads, one lock"). Don't say "JS is like Python" — Python has two models, and JS matches only the asyncio one.

9 · Rate limiting & Redis

The implementation task that kicked all this off. Rate limiting answers two questions: who is asking, and how many times recently.

Redis & INCR

Redis is a key-value store — mentally, a big map of string → string. INCR is a Redis command: "increment this key's value by 1, return the new value." Crucially it's atomic — concurrent INCRs never lose updates, which is what makes it a safe rate-limit counter. Keys can carry a TTL (EXPIRE) — after which Redis auto-deletes them.

key = "rl:discover:1.2.3.4"
count = redis.INCR(key)              # atomic increment
if count == 1: redis.EXPIRE(key, 3600)   # first hit? start the window
if count > 5: return 429              # over the limit

Fixed window vs sliding window

Same "limit", different definition of which 60-second period to look at. Example — limit "3 per minute", 6 requests timed across a window boundary:

ApproachHowResult on the burst
Fixed windowone counter + TTL; resets when the TTL expires — a discrete reset event you can gamelets 6 through in 63s (3 before the reset, 3 after) — the boundary bug
Sliding windowstores individual timestamps; recomputes the count over the trailing 60s on every requestlets 4 through — old requests roll off continuously, no boundary to exploit

Fixed is cheap (1 INCR + 1 EXPIRE) and fine for a POC. Sliding is more accurate but 2–3× the Redis ops. Either way, per-IP limits cap per-attacker cost — a botnet with many IPs still gets through, which is why a global cost cap (the GCP kill switch) is the real ceiling.

The X-Forwarded-For trap & --proxy-headers

Behind a proxy (Railway's edge), the proxy opens a new TCP connection to your app — so request.client.host is the proxy's IP, not the user's. The real IP is in the X-Forwarded-For header.

  • --proxy-headers tells uvicorn: "trust X-Forwarded-For and rewrite request.client.host from it" (it fixes the http/https scheme from X-Forwarded-Proto too). Prod-only — locally there's no proxy.
  • Without it, every user collapses into one rate-limit bucket (the proxy's IP) — "5/hour per IP" silently becomes "5/hour for the whole internet".
  • Trust: only believe the header from your own proxy — anyone can spoof X-Forwarded-For in a raw request. --forwarded-allow-ips is the "which proxies do I trust" half.

Vocabulary picked up

Edge protectionmechanisms that run at the boundary of your system, before requests reach your app (Cloudflare, a CDN's bot-fight mode). "App-level only" = no edge layer, all protection inside FastAPI.
slowapia Python library that plugs rate-limiting decorators into FastAPI; uses the limits library underneath; storage backend is just a config string (memory:// or redis://…).
Hardeninga loose term for the category of work that makes a system resistant to abuse / attack / failure — rate limits, secrets out of code, input validation, CORS allowlists, etc. Not features; robustness.
headers_enabledslowapi flag — adds informational X-RateLimit-* headers so a well-behaved client can see its budget. Informational only; doesn't change enforcement.

10 · Glossary

CPU-bound
— work bottlenecked by computation; a CPU core pinned at 100%.
I/O-bound
— work bottlenecked by waiting on something external (network, disk, DB); CPU mostly idle.
Concurrency
— multiple tasks in progress over the same period, interleaved on one thread.
Parallelism
— multiple tasks executing at the same instant on different cores.
Preemptive multitasking
— an external scheduler can interrupt a task anytime (OS threads).
Cooperative multitasking
— tasks voluntarily yield control at explicit points (asyncio, JS event loop).
Coroutine
— what an async def call returns: an inert "frozen plan" that does nothing until driven by await / create_task / asyncio.run.
Task
— a coroutine that's been registered with the event loop so it runs concurrently. Created by asyncio.create_task.
Event loop
— the scheduler at the heart of asyncio/JS: runs a ready task until it suspends, then picks the next.
Semaphore
— a counter used as a permit pool; acquire takes a permit (or waits), release returns one. Semaphore(1) = a lock.
Lock / mutex
— ensures only one thread is in a critical section at a time; acquire blocks until free.
Race condition
— a bug where the result depends on the nondeterministic interleaving of concurrent tasks touching shared state.
GIL (Global Interpreter Lock)
— CPython's single lock; only the thread holding it runs Python bytecode. Released during I/O.
Thread
— a unit of execution inside a process; threads in one process share memory.
Process
— a running program instance with its own private memory; heavyweight.
Worker (JS)
— an isolated extra JS context (own heap), communicating by message passing — JS's equivalent of multiprocessing.
Redis
— in-memory key-value store; used here for atomic rate-limit counters (INCR + EXPIRE).
TTL
— time-to-live; how long a Redis key survives before auto-deletion.
X-Forwarded-For
— HTTP header a proxy adds to record the original client IP; trustworthy only when added by your own infrastructure.
